# Спринт 1: Архитектурный каркас и модель данных

Ваша задача на этом этапе — заложить правильный фундамент приложения (Clean Architecture / Vertical Slice — на ваш выбор, но с жестким разделением ответственности).

## 1. Структура решения (Solution)

Создайте решение и разбейте его на слои (или проекты):

- CoreLedger.Domain — сущности, перечисления, доменные исключения, интерфейсы репозиториев (никаких зависимостей от EF Core или ASP.NET!).
- CoreLedger.Application — бизнес-логика, сервисы/хендлеры (можно использовать MediatR или чистые сервисы), DTO, валидаторы.
- CoreLedger.Infrastructure — DbContext, конфигурации сущностей (Fluent API), миграции, реализация репозиториев.
- CoreLedger.Api — контроллеры (или Minimal APIs), Middleware, конфигурация DI.

## 2. Доменная модель (Entities)

Реализуйте следующие сущности в Domain:

- User: Id (Guid), Email, FullName, CreatedAt.
- Account (Счет): Id (Guid), UserId, Currency (Enum: RUB, USD, EUR), Balance (decimal), Status (Active, Blocked), RowVersion (для оптимистичной блокировки).
- Transaction (Транзакция): Id (Guid), IdempotencyKey (Guid или string — уникальный ключ операции от клиента), FromAccountId (nullable, если это пополнение), ToAccountId (nullable, если это вывод), Amount (decimal), Type (Deposit, Withdrawal, Transfer), Status (Pending, Completed, Failed), CreatedAt.

## 3. Требования к БД (Infrastructure)

- Настройте AppDbContext и конфигурации через IEntityTypeConfiguration<T>.
- Важно: Для денег (Balance, Amount) явно задайте точность в БД: decimal(18, 4).
- Настройте уникальный индекс на IdempotencyKey в таблице транзакций и на Email в таблице пользователей.
- Поднимите PostgreSQL локально (через docker-compose.yml в корне репозитория) и накатите первую миграцию.

## 4. Базовые эндпоинты (API)

Реализуйте пока без сложной бизнес-логики (просто CRUD с сохранением в БД):

- POST /api/users — создание пользователя.
- POST /api/accounts — открытие счета для пользователя (начальный баланс = 0).
- GET /api/accounts/{id} — получение информации о счете.
